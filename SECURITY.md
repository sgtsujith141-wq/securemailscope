# Security and privacy policy

SecureMailScope analyses packet captures of email traffic. Those captures can
contain authentication credentials, message bodies, recipient lists and other
personal data. The project is built on the assumption that **capture data is
the most sensitive thing in the room**, and that a capture file is untrusted
input.

## Guarantees the code makes

| Guarantee | How it is enforced |
|---|---|
| Analysis is entirely local | No HTTP client, socket, or DNS lookup exists anywhere in the package |
| No captured host is ever contacted | `securemailscope.scapy_guard` replaces Scapy's neighbour resolver with one that raises |
| No telemetry, no cloud AI calls | No outbound client of any kind is imported |
| No shell command is built from a filename | No `subprocess`, `os.system` or `shell=True` anywhere in the package |
| Reports contain no application payload | The payload lives only in the in-memory reassembler; serialisation emits counts, offsets and digests |
| Reports contain no filesystem paths | Only the capture's base name is recorded |
| Resource use is bounded | Eight configurable hard limits, all checked; see `.env.example` |

Two of these are covered by tests that fail loudly if the property is lost:
`tests/test_passive.py` asserts no socket and no subprocess during analysis and
that Scapy's live neighbour resolution raises; `tests/test_report.py` asserts
that known fixture payload text never appears in a serialised report.

### About the Scapy guard

Scapy is primarily a packet *crafting* library. Building an Ethernet layer with
an unresolved destination MAC address makes it emit a **live ARP or Neighbour
Solicitation** on the local network. This was observed during development, not
hypothesised. Importing `securemailscope` installs a guard that replaces the
neighbour resolver so any such path raises `PassiveModeViolation` instead of
transmitting. The read path additionally strips link-layer headers by hand and
hands only IP bytes to Scapy, keeping the crafting machinery out of analysis
entirely.

## Never commit

- Real packet captures (`*.pcap`, `*.pcapng`, `*.cap`, …)
- Email contents, message bodies, address lists
- Passwords, API tokens, session cookies
- Private keys, certificates with private material, PKCS#12 bundles
- TLS key log files (`SSLKEYLOGFILE` output)
- `.env` files or any local configuration holding secrets
- Anything under `tests/fixtures/generated/`

`.gitignore` excludes all of these by default. `scripts/check_staged.sh`
(`make secrets-check`) is a second line of defence that refuses to proceed if
any of them are staged. Neither is a substitute for looking at
`git status` before you commit.

Only **synthetic** captures generated by `securemailscope.testing.fixtures`
may be regenerated locally, and even those are gitignored — the generator and
the expectation manifests are committed instead, so the captures are
reproducible byte for byte without ever being stored in git history.

## Handling real captures

- Keep them outside the repository directory.
- Treat a capture as you would treat the mailbox it came from.
- Get authorisation before capturing or analysing traffic you do not own.
- Reports are payload-free by design, but they still disclose IP addresses,
  ports, timestamps and byte counts. Review one before sharing it.
- Delete captures when the analysis is done.

## Dependencies that fetch from the network

Installation (`pip install -e ".[dev]"`) downloads `scapy`, `pydantic`,
`pytest`, `ruff` and `mypy` from PyPI. This is the only outbound network
activity associated with the project and it happens at install time only.
Pinned versions are in `pyproject.toml`. The application itself performs no
network I/O at any point.

## Reporting a vulnerability

This is a hackathon project under active development and has not been audited.
If you find a security problem, open a private issue on the repository rather
than a public one, and include the capture characteristics that trigger it —
never the capture itself.

## Known security-relevant limitations

See [docs/threat-model.md](docs/threat-model.md) for the full analysis and
[docs/limitations.md](docs/limitations.md) for what passive analysis cannot
determine. The most important points:

- Parsing untrusted captures is inherently risky. Scapy's dissectors are
  written in Python and are not hardened against adversarial input. Analyse
  hostile captures in an isolated environment.
- Reconstruction of overlapping segments follows a documented policy
  (`FIRST_OBSERVED_WINS`) that may differ from the endpoint that actually
  received the traffic. Conflicts are reported rather than resolved silently.
- The engine does not and will not attempt to decrypt TLS.
