## Provenance

Every sample is a **real capture analysed by the real analyzer**. The generator
writes pcap bytes; the M1–M5 engine reconstructs the session; the feature
extractor reads the resulting observations. There is no shortcut path that
fabricates features directly, so a bug in the analyzer shows up in the dataset
instead of being hidden by it.

Explicitly **not** used: downloaded captures, enterprise traffic, private
email, any third-party dataset, any real server. No network access occurs at
any point in generation, training or inference.

The synthetic certificate authority mints throwaway keys in memory. None is
committed; a 1024-bit RSA key is generated only so that a weak key is
*observable* in a capture, and it protects nothing.

Imbalanced, deliberately and realistically: careless servers are a minority.
All classification metrics are macro-averaged for that reason.

### Controlled variation

TLS 1.2 and TLS 1.3 configurations; AEAD, CBC, 3DES, RC4 and NULL suites;
observable and unobservable key-exchange groups; EC, RSA-2048, RSA-1024 and
Ed25519 certificates; certificate lifetimes from 7 to 7300 days; SHA-256 and
SHA-1 signatures; five client capability profiles; ordinary certificate
renewals; and sessions cut short before the server's answer.

**96 of 608 sessions never negotiate at all** — 19%, from a client and server
with no common ground, plus an 8% truncation rate. These are real evidence gaps
and are excluded by the evidence floor rather than being scored.

**320 of 608 sessions carry an observable certificate.** The remainder are TLS
1.3, where the Certificate message is encrypted, or truncated before it.

Capture sizes: 608 files, 362–1271 bytes, 540,511 bytes total.

## Reproducibility

Seeds are part of the dataset definition: population `20260921`, sessions
`815`, split `4242`.

Reproducible: the servers, the clients, the negotiations, the labels, the split
and the content digest. Verified by a test.

**Not byte-for-byte reproducible.** The authority mints a fresh key per
certificate, and ECDSA signatures vary in DER length between runs, so captures
differ by a byte or two *inside the certificate* while describing the same
sessions. This is stated rather than papered over; `capture_size_profile()`
measures the variation.

Library versions are recorded in every model manifest: Python 3.12.14,
scikit-learn 1.5.2, numpy 2.1.3, scipy 1.18.1, joblib 1.6.0.

## The three kinds of truth

The directive requires these to be kept apart, and the design turns on it.

### 1. Forensic ground truth

What the generated capture actually contains: which version and suite were
negotiated, whether a certificate was sent. Used **only** to check the analyzer
read the capture correctly — a test asserts zero mismatches between what the
generator wrote and what the pipeline reported.

### 2. Security policy label

How the M4 policy evaluates the observed session. **Never used as an ML
target.** The assessment layer is switched off while the dataset is built.

### 3. ML evaluation label

Defined independently, in two forms.

**For classification** — the server's latent posture class, from the rubric in
`posture_class()`:

| Class | Criterion, applied to the server's **whole** configuration |
|---|---|
| `CRITICAL` | Will negotiate a NULL or RC4 suite with *some* client |
| `HIGH` | Permits 3DES or static RSA, or accepts a version below TLS 1.2, or presents an RSA key under 2048 bits |
| `MODERATE` | Modern floor and no prohibited suite, but permits CBC, issues certificates lasting over 825 days, or keeps a legacy listener enabled |
| `LOW` | TLS 1.2+, AEAD only, strong key, short lifetime, no legacy listener |

The rubric is informed by RFC 9325 and the widely used Mozilla TLS
configuration tiers. It is a **project-defined ordering**, not a reproduction of
either, and it is applied to the *server* rather than to a session.

Its dependence on unobservable properties is the point: `legacy_listener_enabled`
and the full supported-suite list are never visible in one capture, so the
label cannot be recovered exactly from the features.

**For anomaly detection** — membership of the `anomalous_combination` family,
declared **before training**:

* **Reference population**: the five common families. This is what "normal"
  means for this dataset, and it is recorded in the model metadata because
  "unusual" has no meaning without it.
* **Injected anomalies**: `anomalous_combination`, pairing properties that never
  co-occur in the reference — a modern AEAD suite in front of a 1024-bit SHA-1
  certificate, ChaCha20 over TLS 1.0, 3DES with a fifteen-year certificate.
* **Negative control**: `hardened_uncommon` — ChaCha20-only, Ed25519, very
  short-lived certificates. Rare, entirely legitimate, and labelled **not
  anomalous**. A detector that flags these is reporting unfamiliarity, and a
  test asserts none is flagged.

Synthetic anomalies are **not** a claim about real attack prevalence. They are
combinations chosen to be absent from the reference population, and nothing
more.

## Split

Grouped by **server instance** so no server appears in two partitions, and a
model cannot score well by recognising a certificate it trained on.

| Partition | Samples | Groups |
|---|---|---|
| Train | 313 | 91 |
| Validation | 98 | 30 |
| Test | 101 | 31 |

Group overlap between every pair of partitions: **none**, asserted by a test.

A second evaluation withholds whole families (`legacy_compatible`,
`hardened_uncommon`) so the test set contains kinds of server the model has
never seen.

## Known limitations

- **Synthetic throughout.** Nothing measured on it transfers to real traffic
  without independent evaluation on representative data, and none has been done.
- **Small.** 152 independent groups; 31 in the test split. Confidence intervals
  on per-class metrics would be wide, which is why none is quoted as if narrow.
- **CRITICAL is the smallest class** — 10 test samples. Its per-class metrics
  are correspondingly uncertain.
- **The rubric is ours.** Defensible and standards-informed, not externally
  validated.
- **Generator-shaped.** The families are ones we designed. A configuration
  pattern we did not think of is not represented.
